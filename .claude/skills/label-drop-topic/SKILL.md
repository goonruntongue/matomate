# Label Drop のお題の作り方（生成ルール）

> 決めた日: 2026-10-03（SPEC 決定事項 #25・#26）。お題は Claude が会話の中で作り、アプリに内蔵する。Workers AI は使わない。
> ユーザーとのやりとりは日本語。作ったお題は、追加する前に一覧（タイトル・brief・グループ名）を見せて確認をもらう。

## 1. 置き場所と形

- 個人モードのお題: `app/src/data/topics-curated.ts` の `CURATED` に足す（書き方は既存の行をまねる。`g(label, altLabels, [[語, 意味], ...])`）。
- 型は `app/src/data/problems.ts` の `Problem`。
  - `id`: 英小文字とハイフン（例 `car-trunk`）。既存と重ならないこと（`grep -rn "id: '" app/src/data` で確認）。
  - `tier`: `everyday`（家の中・身の回りの物）／`service`（だれもが使うお店・サービス・アプリ）／`web`（実際のサイトの IA）。
  - `brief`: `{ user, scene, goal }` ＝ だれが・どんな場面で・何のために。
  - `axisHint`: 分ける軸のヒント。
  - `groups`: 5つ。各 `{ label, altLabels, items }`。
- 教室モード用のお題（作り直し）は、上に加えて **「別の目的の例」** を持つ（5 を参照）。型への項目の追加は、教室モードの実装（CLASSROOM_SPEC の段階5）のときに行う。それまでは案を会話と `docs/` に残す。

## 2. 数と長さ（`worker/src/ai/validate.ts` と同じ基準）

| 項目 | 決まり |
|---|---|
| グループ | **ちょうど5つ** |
| 1グループの語 | **ちょうど6語**（全部で30語） |
| title | 2〜20字 |
| brief の各項目 | 2〜48字 |
| axisHint | 8〜110字 |
| label（グループ名） | 2〜10字 |
| altLabels | **各グループに2つ**。1〜14字 |
| 語（text） | 1〜12字 |
| 語の意味（desc） | 2〜40字。**1行で、その語の意味だけ**を書く（どのグループかは書かない） |

## 3. 中身のルール（ここが品質の中心）

1. **軸は1つ**。5グループすべてが、同じ問い（例：「どんな場面で取り出すか」）への答えになっていること。「場所」のグループと「使う人」のグループを混ぜない。
2. **境目のあいまいな語を入れない**。どの語も、brief の目的に照らせば1つのグループにしか入らないこと。2つに入りうる語は、別の語に替える（どうしても残すなら `data/flexibleItems.ts` で「どちらでも正解」にできるが、なるべく使わない）。
3. **同じ物の重複なし**。表記ゆれ（全角半角・カタカナ／ひらがな）や、ほぼ同じ物（「ゴミ袋」と「ポリ袋」など）を2つ入れない。
4. **何でも入る受け皿グループを作らない**（「その他」「便利グッズ」「いろいろ」など）。
5. **語にグループ名を含めない**（グループ「掃除」に「掃除機」を入れない＝答えが見えてしまう）。
6. **axisHint にグループ名を書かない**。軸の「問い」と、具体的な語を1つ使った例の問いかけで書く（例：「『どんな場面で取り出すか』で考えてみましょう。たとえば『ジャッキ』を取り出すのは、どんなときでしょう？」）。
7. **brief は具体的に**。だれ（例：4歳と6歳の子どもがいる家族）・場面（例：おもちゃが散らかり、子どもが自分で片付けられないとき）・目的（例：おもちゃ箱ごとに、入れるおもちゃを決める）。目的は「〜ごとに、〜を決める」の形にすると、箱の意味が伝わる。
8. **だれでも思い浮かぶ語を選ぶ**（特に everyday）。専門用語や地域・世代で通じない語は避ける。分かりにくい語は desc で補う。
9. **ラベルは短く、利用者の言葉で**。altLabels は「同じ意味の言い換え」（採点で同じ意味とみなす）。ちがう意味の言葉を入れない。
10. 既存のお題（`app/src/data/` の全ファイル）と、題材も語の組み合わせも似すぎないこと。

## 4. 作るときの手順

1. 題材を決め、brief を書く。
2. 軸の問いを1つ決める（「◯◯で考える」と1文で言えるか）。
3. その問いへの答えとして、重ならない5グループを決める。
4. 各グループに6語。1語ずつ「ほかのグループに入らないか」を確かめる。
5. desc、altLabels、axisHint を書く。
6. 3 の各ルールで自分で見直す。特に「軸の混在」「境目の語」「重複」「受け皿」。
7. ユーザーに一覧を見せて確認をもらってから、ファイルに足す。
8. `npm --prefix app run typecheck` と `npm --prefix app run build` を通す。可能なら dev サーバーで、そのお題が出ることを確かめる。

## 5. 教室モード用のお題（作り直し、SPEC #26）

教室モードでは、**固定課題**（お題の目的で分ける）のあと、**同じブロックで、チームが自分で決めた目的で分け直す自由課題**がある（箱は2〜5個、🗑️ ゴミ箱に要らない語を捨てられる）。そのため、教室モード用のお題には次も求める。

1. **いくつもの目的で分けられる語の集まり**にする。固定課題の軸のほかに、**少なくとも2つ、まったく別の軸で自然に分け直せる**こと。
   - だめな例：100均の商品（値段はどれも同じなので「値段」で分けられない）、軸以外の性質がそろいすぎた語。
   - よい例：語ごとに「使う場所」「使う人」「使う頻度」「大きさ」「季節」など、いくつもの性質がばらばらに散らばっている。
2. 固定課題のルール（2・3）はそのまま守る。固定課題の目的では、境目のあいまいな語がないこと。
3. **別の目的の例を2〜3個**作る。各例は：
   - brief と同じ形（だれが・どんな場面で・何のために）。固定課題の目的とは、**分け方がはっきり変わる**もの。
   - 確かめ用の分け方のスケッチ：箱（2〜5個）の名前と、捨てそうな語。これで「本当に分け方が変わるか」「30語の多くが使えるか」を確かめる（プレイヤーに答えとして見せるかは CLASSROOM_SPEC 7.0 で決める）。
   - 例（動物園）：固定＝来園者向けの「エリアの案内」→ 別の目的＝「飼育員の餌やり当番表（何を食べるか）」「子ども向けクイズラリー（住んでいる地域）」。
4. 3 の例の中で、**移るブロック**（固定課題とちがう箱に入る語）が多いほど、発表で違いが見えやすい。半分以上の語が移るのを目安にする。
5. ゴミ箱に捨てる語が多すぎる例は避ける（ゴミ箱には容量の上限がある）。

## 6. 監修（すでにあるお題を見直すとき）

- 3・5 のルールで1問ずつ判定し、「そのまま」「直す（どこをどう）」「やめる」を、理由を添えて一覧にしてユーザーに見せる。
- 直した記録は、必要なら `worker/review/curated/<日付>.json` と同じ形で残す（過去の判定の例がある）。
