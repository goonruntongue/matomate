# みんなでラベル（Label Drop の教室モード）仕様書（下書き）

> 作成: 2026-10-03（構想段階。実装は未定）
> 目的: IT講師の教室で、ログインした生徒がチームを組み、同じお題をリアルタイムに相談しながら仕分け・名付けをして、全チームの結果を見比べて話し合えるようにする。
> **別アプリとして作る**（2026-10-03 決定、SPEC #27）: 今の Label Drop には手を加えず、そのまま残す。教室モードは Label Drop を元にした**別のアプリ**として完成させ、**別の URL で配信**する。この文書の「教室モード」は、その別アプリのこと。
> - **アプリの名前: 「みんなでラベル」**（2026-10-03 決定。シリーズでは「practice IA ─ みんなでラベル」）。
> - **ソースの置き場所**: このリポジトリ（IA-DX）の **`classroom/`** フォルダ。API は今の `worker/` を使う。
> - **作り方**: 今の `app/` を `classroom/` へ**コピーして、そこから育てる**（Label Drop の `app/` とはコードを共有しない。片方を直しても、もう片方に影響しない）。
> 前提: Cloudflare は**無料プランのまま**（SPEC 8.1）。お題は Claude が作って監修したもの（アプリに内蔵）を使い、Workers AI は使わない（決定事項 #25）。

## 0. 教室モードの目的と、課題の進め方（2026-10-03 決定、SPEC #26）

### 0.1 目的
- 教室モードは、正解・不正解の得点で先へ進むゲームではない。**「どんな目的で分けるかによって、グループの分け方も、付ける名前（ラベル）も変わる」ことを体感し、チームで話し合う学習教材**として作る。
- 今のお題は目的（だれが・どんな場面で・何のために）が決まっているので、1問だけでは「目的が変わると構造が変わる」ことは伝わらない。一方で、最初から目的を決めずに分けると、自由すぎて難しくなりすぎる。
- そこで、**目的が決まった課題で型を覚えてから、同じブロックで目的を自分たちで決めて分け直す**、という2段階にする。

### 0.2 Label Drop（個人で遊ぶ版）との違い
- **教室モードは別アプリ**。入口（URL）を分け、今の Label Drop はグレードアップせずにそのまま残す。
- **レベルアップは教室モードでは使わない**（レベル・称号・最終試験・👑 はなし）。Label Drop はレベルアップも含めて今のまま。

### 0.3 2つの課題
| | **固定課題** | **自由課題** |
|---|---|---|
| 目的 | お題に決まっている（例：動物園の案内、100均の売り場の掲示） | **チームが自分たちで決める**（だれが・どんな場面で・何のために） |
| ブロック | お題から配られたもの | **固定課題と同じブロック** |
| 箱の数 | 今と同じく自動で決まり、固定 | **2〜5個の範囲で増やしたり減らしたりできる** |
| 🗑️ ゴミ箱 | なし | **あり**。その目的では要らないブロックを捨てる。中身はいつでも開いて確かめられ、戻せる。**容量に上限**がある（全部は捨てられない。**配られたブロックの3分の1まで**、端数は切り捨て。例：30個なら10個、10個なら3個） |
| 目的の数 | 1つ | **複数のスロット（1チーム3つまで）にストックできる**（目的Aで分けて保存 → 目的Bで分け直して保存…）。チームはそのうち1つを**第一候補**に選ぶ |
| 終わり方 | 提出 | **チームの「提出」で終わる。制限時間はなし** |
| 答え合わせ | **発表のときに**作者の分け方と比べた結果（★・一致数・ラベルの判定）を出す。解いている途中には出さない | 正解はない。発表で、目的と分け方の説明を聞き合う |

- 自由課題の目的は、今の brief と同じ「**だれが・どんな場面で・何のために**」の型で書く。手が止まらないように、お題ごとに Claude が作った「**別の目的の例**」を2〜3個用意し、**「例を見る」ボタンを押したときだけ**見せる（例から選んでも、自分で考えてもよい）。

### 0.4 出題パターンと流れ
- 管理者（セルフモードではホスト）が、出題パターンを選ぶ。
  - **両方**（既定）：固定課題 → 発表 → 自由課題 → 発表
  - **固定のみ**：固定課題 → 発表
  - **自由のみ**：自由課題 → 発表
- 発表と課題を交互に進める。

### 0.5 発表
- 固定課題の発表：全チームの分け方とラベルを並べ、作者の分け方と比べた結果（★など）をここで初めて見せる。
- 自由課題の発表：チームごとに「**目的 → 分け方とラベル → 固定課題から何が変わったか**（移ったブロック、捨てたブロック、箱の数）」を見せる。スロットは**全部見られる**ようにし、**第一候補を最初に**見せる（ほかのスロットは切り替えて見る）。
- 発表のあいだは、発表しているチームの画面を全員に映す（管理者／ホストが切り替える）。

### 0.6 お題
- 今のお題は「軸が1つ」になるように作ってあるため、別の目的では分けにくいものがある（例：100均の商品はどれも値段が同じ）。
- 教室モード用に、**いくつもの目的で分けられるお題を作り直す**（Claude が作る）。作るときのルールは、ローカルスキル `.claude/skills/label-drop-topic/SKILL.md` にまとめた。今後お題を増やすときも、このスキルに従う。

## 1. 進め方は2つ

| | **講師モード**（管理者が進行） | **セルフモード**（管理者なし） |
|---|---|---|
| 想定 | PC教室の授業。講師が全体を見ながら進める | 自習、勉強会、講師が不在のとき、オンラインだけの集まり |
| 部屋を作る人 | 管理者 | ログインしている人ならだれでも（作った人が「ホスト」） |
| チーム分け | 管理者がチーム数・チーム名を決め、参加者が選ぶ | 参加者が選ぶか、ホストが「自動で振り分け」 |
| お題の選び方 | 管理者が選ぶ（種類・ブロック数） | ホストが選ぶか「おまかせ（ランダム）」 |
| 結果発表 | 管理者が「結果を見せる」の可否を決める | 全チームが提出したら自動で発表（制限時間はなし） |
| 次の問題 | 管理者が始める | ホストが始める／全員の「次へ」投票 |
| 全チームの途中経過 | 管理者だけが見られる | だれも見られない（発表まで） |

両モードは同じ仕組みの上で動く。違いは「だれが進行の権限を持つか」と「自動で進むか」だけ。

## 2. 役割と権限

| 役割 | なれる人 | できること |
|---|---|---|
| **管理者** | 管理者リストのアカウント（最初は goonruntongue@gmail.com） | 管理画面を使う：部屋の作成・終了、チーム数とチーム名、お題とブロック数、全チームの途中経過と回答の閲覧、結果ボタンの表示切り替え、結果発表、次の問題、管理者の追加・削除 |
| **ホスト** | セルフモードで部屋を作った人（引き継ぎ可） | 自分の部屋だけ：チーム設定、お題選び、開始、結果発表、次の問題。**他チームの途中経過は見られない** |
| **参加者** | ログインしている人 | 部屋とチームを選んで参加、自分のチームの盤面の操作、チームのチャット、他チームの「未／済」バッジの確認、結果画面とそのチャット |

- ホストが抜けたら、次に入室した順の参加者へ自動で引き継ぐ（セルフモードが止まらないように）。
- 管理者は、セルフモードの部屋にも入って見守れる（介入はしない）。

## 3. 画面と流れ

### 3.1 ログイン（OAuth）
- Google でログイン（OAuth 2.0 / OpenID Connect）。**個人の Google アカウント**を想定し、ドメインでの参加制限はしない。生徒が Google アカウントを持たない場合に備えて、**部屋コード＋表示名だけで入れる「ゲスト参加」**を部屋ごとに許可できるようにする（講師が選ぶ）。
- 方式は 4.2 の比較を参照。

### 3.2 ロビー
- 参加できる部屋の一覧（講師モードの部屋は、管理者が開いている間だけ表示）＋「部屋コードで入る」。
- 部屋に入ると、チームの一覧（チーム名・人数）が出て、参加者は1つを選ぶ。

### 3.3 管理画面（管理者のみ）
- 部屋の設定：チーム数と1チームの人数の上限（**管理画面で自由に変えられる。既定は5チーム×4人＝20人**）、チーム名、ゲスト参加の可否。
- 出題：お題の種類（tier：身近な題材／身近なサービス／Webサイト、または個別のお題）、ブロック数。
- 監視：チームごとの参加者、盤面の進み具合（仕分け済みの数・ラベル）、チャット、提出の有無。
- 結果：「参加者に結果ボタンを出す」のオン／オフ、「結果発表」ボタン（全チーム提出の通知を受けて押す）。
- 次の問題を始める／部屋を閉じる。
- 管理者アカウントの追加・削除（自分自身は消せない。最後の1人は消せない）。

### 3.4 チームで解く
- 部屋の全員に、同じお題・同じブロックが配られる（4.4 の「同じ盤面の作り方」）。
- **チームの盤面は共有**：だれかがブロックを箱へ投げ入れると、同じチームの全員の画面に反映される。ラベルの入力も共有（入力中の人の名前を表示）。
- チームのチャット欄（チームのメンバーだけが読める）。
- 画面の上に、各チームの「未／済」バッジ（提出したかどうかだけ。中身は見えない）。
- 提出：チームのだれかが「提出」→ 確認ダイアログ → チームの回答が確定（取り消しは管理者／ホストだけ）。

### 3.5 結果発表
- 発表のきっかけ：
  - 講師モード：結果ボタンが「表示」の設定なら、全チームが提出した時点で参加者に「結果を見る」ボタンが出る。「非表示」の設定なら、管理者が「結果発表」を押した瞬間に、全員の画面が結果画面へ切り替わる。
  - セルフモード：全チームが提出した時点で自動で切り替わる（制限時間はなし）。
- 結果画面：全チームの分け方とラベルを並べて表示し、模範との比較（今の答え合わせと同じ ★・正解数・ラベルの判定）を出す。全員が書けるチャット欄つき。
- 次の問題：管理者（講師モード）／ホスト、または全員の「次へ」の過半数（セルフモード）。

## 4. 仕組み（Cloudflare 無料プランで作る）

### 4.1 構成

```
ブラウザ（今のゲーム＋教室モードの画面）
   │  HTTPS / WebSocket
   ▼
Worker（label-drop-api）── ログイン、部屋の一覧、管理者リスト、履歴（D1）
   │
   ▼
Durable Object「Room」（部屋ごとに1つ）── 部屋の状態・チームの盤面・チャットを持ち、WebSocket で全員に配る
```

- **Durable Objects**（SQLite 型）は無料プランで使える。無料枠を超えるとエラーになるだけで課金されない（2026-10-03 に公式ドキュメントで確認）。
- WebSocket は **Hibernation API** を使う（話していない間は課金対象の時間を使わない設計。無料枠の節約になる）。
- 1部屋＝1つの Durable Object。部屋の中の状態（参加者、チーム、盤面、チャット、提出、フェーズ）はその中の SQLite に置き、部屋が終わったら要約だけ D1 の履歴へ。

### 4.2 ログイン方式の比較

| 方式 | よい点 | 注意点 |
|---|---|---|
| **A. 自前の Google OAuth**（Worker でコード交換、署名付き Cookie） | Cloudflare の追加設定や支払い方法の登録が不要。ゲスト参加と組み合わせやすい | Google Cloud でクライアントIDを作る手間。実装量は中くらい |
| B. Cloudflare Access（Zero Trust） | 実装がほぼ不要（SPEC 8.5 の `AUTH_MODE=access` が使える） | 有効化のとき支払い方法の登録を求められることがある。無料は50人まで。ゲスト参加を混ぜにくい |

→ 教室で生徒を入れるなら **A を推奨**。

### 4.3 無料枠の見積もり（30人・1回90分の授業。既定の想定は20人なので、さらに余裕がある）
- WebSocket のメッセージ（ブロック移動・ラベル入力・チャット）：1人1分あたり10件として 30人×90分×10 ＝ 約27,000件。Durable Objects のリクエストは、WebSocket の受信メッセージが20件で1件に数えられる（料金表の記載。実装時に最新を確認する）ので、実質 約1,400件。無料枠（1日あたりの上限は実装時に確認する）に十分収まる見込み。
- D1：履歴の保存は1問1チーム数行。問題にならない。
- 授業を1日に何コマも続けても、余裕がある見込み。実装後に実測して確かめる。

### 4.4 同じ盤面の作り方
- お題はアプリに内蔵（静的）。サーバーは「お題のID・ブロック数・乱数の種」だけを配り、各ブラウザが同じ手順で同じブロックを作る（今の `freshBoard` を、乱数の種を受け取れる形にする）。
- チームの盤面は、操作（「ブロックXを箱Yへ」「箱Yのラベルを〜に」）を Room に送り、Room が順番を決めてチームの全員へ配る。同時に同じブロックを動かした場合は、Room に先に届いた方を採用する。
- 3D の「投げる」演出は各自の画面だけ。共有するのは結果（どの箱に入ったか）だけ。

### 4.5 見せる・見せないの守り方
- 他チームの盤面とチャットは、**サーバー（Room）が送らない**ことで隠す（画面で隠すだけにしない）。
- 管理者かどうかは、ログインのたびにサーバー側の管理者リストで判定する。

## 5. データ（案）

- D1：`users`（ログインした人）、`admins`（管理者リスト）、`rooms`（部屋の一覧・モード・作成者）、`results`（問題ごと・チームごとの回答と点数の履歴）。
- Room（Durable Object の SQLite）：`members`（人・チーム・役割・接続中か）、`teams`、`board`（チームごとの配置とラベル）、`chat`（チーム別／結果画面）、`round`（お題・フェーズ・提出状況）。

## 6. 段階的な作り方（提案）

1. **ログインと部屋**：Google OAuth、ロビー、部屋への入室、チームの選択（盤面はまだ各自）。
2. **共有盤面とチャット**：Room の WebSocket、チームの盤面の同期、チームのチャット、「未／済」バッジ。
3. **講師モード**：管理画面（出題・監視・結果ボタンの切り替え・結果発表・次の問題・管理者の追加削除）。
4. **結果発表**：全チームの比較画面、結果チャット、全員の画面の切り替え。
5. **自由課題**：目的の入力（だれが・どんな場面で・何のために）、箱の数の変更（2〜5）、🗑️ ゴミ箱、スロットへのストック、出題パターン（両方／固定のみ／自由のみ）、自由課題の発表画面。
6. **セルフモード**：ホスト、自動振り分け、自動発表、「次へ」投票、ホストの引き継ぎ。
7. 履歴と振り返り（チームごとの成績の推移など）。

各段階で、教室（30人前後）を想定した負荷のテストをしてから次へ進む。
